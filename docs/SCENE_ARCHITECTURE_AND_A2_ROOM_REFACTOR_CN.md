# Nereis-Hero 场景结构与 A2 房间化改造方案

> 目标分支：`feature/story-map-progression`
> 状态：架构审计与分阶段改造约定；不是房间拆分已完成的声明。

## 1. 当前问题

- `scenes/` 同时放置可玩区域、入口/流程场景、演示场景、测试场景和专用子场景；根目录职责不够清晰。
- `scripts/levels/greybox_world_region.gd` 是约 242 KB 的共享控制器，集中承载平台布局、地面与绘制、出生点、出口、线索、拾取物、敌人、隐藏路线、A5 房间组装以及多个区域的特殊逻辑。它已成为修改风险和定位成本的主要来源。
- A2 的区域入口仍为 `scenes/ash_forest.tscn`，但地形已经拆成六个可编辑房间场景；区域控制器保留主角、镜头、HUD、跨区出口与世界状态，不再逐条创建这 61 个主要平台节点。
- 已有 A5 room assembly 是可以参考的先例，但不应未经审计直接复制，因为它的组装、内部连接和状态刷新包含 A5 专用分支。

## 2. 目标架构

### 区域层（Region）

区域负责地图总账、跨房间连接、存档状态和区域级流程，不再直接持有所有房间的具体平台细节。

### 房间层（Room）

房间是具有明确边界和职责的可独立编辑场景。建议 A2 第一轮按自然地形分为：

- `A2-R01` 林间入口与岔路
- `A2-R02` 树冠层与 C03
- `A2-R03` 钟墓上层
- `A2-R04` 钟墓坑底与回程
- `A2-R05` 朝圣高路与 C04
- `A2-R06` 东侧沟壑与 C03 远端落点

六个房间场景按地形职责拆分，但当前仍由 `scenes/ash_forest.tscn` 一次性装配成一张连续的 A2 大地图；它们不是六张依次切换、会截断探索流程的关卡。后续只有在明确的门/落差边界确有需要时，才增加真实房间转场。

### 连接层（Connection）

每条连接需要明确：源房间/出口、目标房间/入口、落点、方向、是否单向、解锁条件、返回规则和测试标识。C03、C04 等现有地图连接合同必须继续引用统一地图总账，不能仅靠场景中画线表示连接。

### 持久状态层（WorldState）

房间切换不得重置已拾取物品、已开启捷径、机关状态、休整点和结局相关事实。房间装配不应把持久状态放在临时房间节点里。

### 当前落地进度（2026-10-23）

- 已将 A2 的 61 个主要平台与 9 个下层回程/沟壑石沿，分别迁入六个 `.tscn` 房间场景；平台由 `StaticBody2D`、`CollisionShape2D`、`Polygon2D` 和 `Line2D` 节点定义，碰撞与可见灰盒外形均属于场景，不再由运行时逐个平台 `new()` 或统一绘制。
- 六个场景职责固定为：R01 林间入口与树根岔路；R02 树冠与断裂桥；R03 钟墓上层；R04 钟墓坑底与回程；R05 旧朝圣高路；R06 东侧沟壑与 C03 远端落点。
- R04 内含 200×40 的钟墓坑底碰撞地板；坑底上方的回程石沿拆成左右两段，中间保留 80px 落差通道；R04/R06 的下层石沿也已移入各自场景。共享区域控制器只读取场景碰撞矩形供可达性/材质数据使用；A2 的平台外形和顶边由场景节点绘制，不会重复绘制。
- 已修正休整点判断：钟墓地表开口止于 x=1060，x=1150 的休整点仍在连续地面。
- 已修复死亡恢复的双重所有权：区域控制器负责 0.75 秒延迟、检查点传送与状态恢复，主角脚本不再并行启动第二套死亡淡出/传送，避免两套流程同时改写位置和战斗状态。
- 静态验收脚本已改为从六个场景读取平台位置与碰撞尺寸，并检查 C03/C04、树冠路线与钟墓坑底的关键合同；尚未宣称已运行该 Python 验收器或 Godot 实机验收。

## 3. 场景目录整理原则

计划将场景按职责分组，而不是一次性批量移动所有文件：

- `scenes/regions/`：玩家实际探索的区域入口场景
- `scenes/rooms/<region>/`：区域内部房间
- `scenes/characters/`：可复用角色场景
- `scenes/debug/`：地图测试、碰撞检查、流程演示
- `scenes/demos/`：独立玩法/结局演示
- `scenes/ui/`：独立 UI 场景（若存在）

目录迁移必须配套更新所有 `res://` 引用、资源 UID/场景依赖和静态检查；在引用盘点完成前，不移动现有入口场景，不改项目启动路径，也不批量重命名场景。

## 4. 共享控制器拆分原则

先把 `greybox_world_region.gd` 作为稳定基线，按职责逐步提取模块；每一步保持原有调用路径或提供兼容委托：

1. 地形定义与碰撞/绘制数据
2. 房间出生点与出口连接
3. 线索、拾取物与交互对象生成
4. 区域状态与隐藏路线刷新
5. 遭遇生成与 AI 激活
6. 特定区域（尤其 A5）的装配专用逻辑

禁止通过降低断言、删除合同检查或只检查字符串存在来制造“通过”。每一步都需要静态检查；Godot 场景导入、碰撞和完整路线仍需本地运行验收。

## 5. 分阶段执行

### S0 — 基线与合同
- 固定当前分支与提交基线。
- 记录入口场景、区域场景、演示/调试场景及引用关系。
- 保留 A0/A1 现状，除非依赖修复确有必要。

### S1 — A2 地图总账
- 完成一张 A2 总图，标注所有房间边界、C03/C04、钟墓落差、隐藏支路、捷径与回程。
- 明确每个连接的目标落点与单向/双向性质。

### S2 — A2 房间化
- 从当前共享控制器生成的地形中提取可复用的房间场景。
- 先完成房间装配与场景切换，再逐步删除旧的 A2 专用生成分支。
- 同一时刻只迁移一组连接，避免一次性重写全地图。

### S3 — 控制器减负
- 将稳定职责逐个提取到小型模块。
- 每次提取保持现有 API/行为，新增测试覆盖调用契约。

### S4 — 场景目录整理
- 引用盘点完成后再分目录迁移。
- 更新静态校验器的入口清单和路径检查。
- 保留明确的兼容入口，避免破坏存档/调试启动路径。

### S5 — 完整验收
- 运行静态拓扑、场景引用、空间可达性和连接合同检查。
- Godot 4.6.1 本地运行验证房间切换、出生点、碰撞、死亡恢复和状态持久化。
- 从 A1 进入 A2，完成树冠/高路/钟墓探索并按设计路线返回；不以孤立房间通过替代完整路线通过。

## 6. 验收约束

- 不启用 GitHub Actions。
- 不把尚未在 Godot 运行的静态检查描述成实机通过。
