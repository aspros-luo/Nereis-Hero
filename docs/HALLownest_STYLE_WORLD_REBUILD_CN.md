# 圣巢式可探索世界重构计划（Nereis Hero）

> 状态：已确认的地图方向；实施中。目标是可实际游玩的分层世界，不是灰盒平台拼接，也不是仅供展示的世界地图图片。
> 分支：`feature/story-map-progression`
> 参照原则：借鉴《空洞骑士》圣巢的宏观空间关系、房间式探索、垂直层次、隐藏入口、单向落差、能力门和捷径回环；不复刻原作地图像素、逐房间几何、美术资产或内容。

## 1. 方向决策

### 停止的工作方式
- 不再以 `greybox_world_region.gd` 的长条关卡为最终地图。
- 不再把在长条场景里增加平台、坑洞、地面线条或远景符号当作地图重构的主要交付。
- 不把宏观拓扑 SVG、JSON 连通性或静态平台数量当成“地图已经做好”。
- 不在新地图尚未成形前删除旧脚本；旧场景暂时只作逻辑迁移参考和回退方案。

### 新目标
- 地图由多个可独立编辑的房间/场景构成；每个区域由若干房间组成，而不是一个超长横向场景。
- 房间具有不同宽高、分层平台、竖井、洞穴、建筑内部、落差和非对称出口。房间边界只用于场景组织，不能让探索体验变成不断点选菜单。
- 区域间连接与区域内连接都必须落到真实门、通道、落井、升降机或能力门上。
- 视觉上形成有辨识度的原创地下王国：前后景层次、环境轮廓、建筑剪影、光照/雾效、地表材质和地标共同表达路线；不能仅用彩色矩形表示地形。
- 玩家能够看到暂时无法到达的高台、封门、远处建筑或深坑，并能在探索后从另一高度或捷径抵达。
- 战斗和剧情暂时不作为地图施工的阻塞条件；先建立完整的主线可通行网络和可选支路。

## 2. 世界空间布局目标

以下是空间职责而非原作房间复制。区域继续使用 Nereis 的 A/H ID 和现有剧情名称。

- **表层入口与回访枢纽**：A0、A1。A0 是紧凑的逃脱序章；A1 是能持续回访的村庄，地表、井下和后期捷径互相连接。
- **中央多向交汇区**：A2、A3。主路线、上层路线、低位通道和侧区入口交错；不能只有左右两个出口。
- **自然区域与分支落差**：A2、A5。曲折地形、树冠/高台、沟壑、坑底、被遮挡的支路与可见的远端目标。
- **地下横向网络**：A4。低顶通道、水闸、竖井和从另一侧开启的回程捷径。
- **竖向建筑/矿区**：A6、A7。多层攀升、单向下落、可从远端解锁的回路，以及高位门和低位门的分离。
- **错位入口的深层迷宫**：A8 与 H 区。不能用直线走廊替代；入口、出口与地标错位，允许迷路但必须可读。
- **大型多层中心区**：A9、A10。上层街区、中层主路、下层水道、建筑内部和跨层连接并存。
- **深层主线与可选真相**：A11、A12、A13。主线推进清晰，隐藏支路丰富但不成为通关的硬门槛。
- **可选侧区**：H01–H08。分别从不同高度/区域侧面进入，拥有独立视觉主题和返回方式。

## 3. 运行时地图架构

实施时优先采用“房间场景 + 连接契约”的结构：

1. 每个房间是独立的 Godot 场景，拥有自己的碰撞地形、背景/前景、入口出口锚点、相机边界和本地地标。
2. 房间出口由数据标识目标房间、目标入口、方向、开启条件和是否单向；禁止把抽象 C-edge 直接当作可走路线。
3. 场景切换必须携带目标入口 ID，而不只使用 `west/east`。切换后角色必须落在有效碰撞地面上，且不能直接进入门的触发区域。
4. 房间内路线使用真正的地形与碰撞；隐藏墙、可破坏墙、落井、升降机、能力门必须有对应运行时行为。
5. 存档记录当前房间、入口/检查点、已开捷径、已发现隐藏入口、能力和区域进度；旧存档通过迁移映射继续可用。
6. 地图界面只反映玩家已发现/已测绘的房间和连接，不替代实际关卡，也不提前泄露隐藏区域。
7. 旧的 `greybox_world_region.gd` 不再承载新房间内容。新架构验证通过前保留它以便逐项迁移现有门、敌人、道具、共鸣路线和结局判定。

## 4. 施工顺序

### M0 — 冻结旧方向并盘点可复用逻辑
- 不再新增共享长条灰盒地形。
- 盘点现有门、存档、出生点、死亡恢复、能力、道具、剧情与结局代码，记录各自依赖的场景路径和区域 ID。
- 明确房间 ID、出口 ID、入口锚点、地图发现状态的数据契约。

### M1 — 先搭完整世界的房间级空间图
- 依据现有 `tools/hallownest_reference_layout.json` 设计原创的全局空间布局。
- 将 A0–A13、H01–H08 拆成多个房间节点；每个房间有层级、尺寸类别、用途、出入口和连接条件。
- 先覆盖所有主线和主要回环，不因分阶段实现而截断整条主线。
- 生成可读的原创房间网络图供开发验收；它是开发工具，不是最终玩家地图。

### M2 — 建立可复用的原创房间美术/地形基元
- 定义地面、斜坡、平台、墙体、门洞、井道、升降机、背景层、前景遮挡、发光地标等可复用资源。
- 使用项目原创素材或明确获授权的素材；不得把原作截图切块当作关卡资产。
- 让地形轮廓、材质和光照具有完整视觉语言；不以纯色矩形作为最终呈现。

### M3 — 实现房间导航与跨房间连续探索
- 实现入口/出口解析、出生点、安全落点、相机边界、场景切换、回程捷径与单向落差。
- 先关闭非必要敌人，实测主角跑、跳、坠落、攀爬/冲刺等已有能力。
- 对每个出口验证双向性、门状态、出生点、死亡恢复和存档恢复。

### M4 — 迁移旧系统并整图验收
- 逐个迁移战斗、交互、道具、隐藏路线、剧情旗标和 Boss 生命周期。
- 旧存档兼容测试；无法映射的状态必须有显式回退规则。
- 从序章开始完整通关主线，再检查所有可选区和能力回访路线；不能只用区域测试菜单逐区启动代替完整流程。

## 5. 验收条件

- [ ] A0 到终局的主线可连续游玩，不需要开发菜单跳关。
- [ ] 所有主线连接都落到真实场景出口与碰撞路线。
- [ ] 至少一个中央区域具有三个或更多有效方向，并通过高低层路线相互连通。
- [ ] 至少一个地下网络有非直线回环与从远端开启的捷径。
- [ ] 单向落差、能力门、隐藏入口和电梯的运行时行为与设计数据一致。
- [ ] 每个出生点落在可站立的碰撞面上，镜头不会暴露未完成的地图边界。
- [ ] 地图视觉不是灰盒矩形堆叠；背景、前景、地形轮廓、材质和地标形成一致的原创风格。
- [ ] 完整流程验证角色移动、碰撞、输入、场景切换、存档、死亡恢复、Boss 与结局。
- [ ] 静态检查和 Godot 运行时检查分别记录，不互相替代。

## 6. 当前诚实状态

- 目前仓库已有区域场景、共享灰盒控制器、拓扑 JSON 和一张宏观拓扑 SVG。
- 这些资产不是房间式圣巢风格世界，也不代表地图已经可玩化完成。
- 本计划记录的是已经确认的方向和验收边界；只有实际代码、场景资源与运行时结果才能证明各阶段完成。
