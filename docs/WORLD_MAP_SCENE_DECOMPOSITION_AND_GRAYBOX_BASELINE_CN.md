> 分支：`feature/story-map-progression`
> 状态：设计执行基线；不是地图完成证明，也不是 Godot 实机验收。
> 前置文件：`tools/world_map_topology.json`、`docs/COMPLETE_WORLD_MAP_ATLAS_CN.md`、`docs/INTERCONNECTED_BOX_WORLD_DESIGN_CN.md`、`docs/MAP_CONTENT_COMPLETION_ROADMAP_CN.md`。
> 当前阶段：先完成世界拓扑与场景拆分审计，再制作/修正灰盒；敌人、NPC、收集品与战斗填充后置。

## 1. 本轮不可偏离的目标

Nereis Hero 的目标是一个可探索数十小时的互联世界，而不是一组通过门串起来的独立关卡，也不是一张不断向右延伸的平台长图。

- 世界地图先确定全部大区域之间的关系。
- 每个大区域内部再设计多方向探索网络：分叉、死路、回头路线、上下层、局部回环、从另一侧开启的捷径、看得见但暂时到不了的地点。
- 最终游戏场景（Godot `.tscn`）只是实现边界，不等同于玩家认知中的大区域或子区域。
- 场景切换可以发生在同一大区域内；只要入口方向、地标、相邻空间和返回落点保持连贯，玩家仍应感到自己在同一片连续地理中探索。
- 先完成可走的灰盒并使用主角实测，再系统填充敌人、Boss、NPC、道具和剧情内容。
- 任何拓扑图、坐标合同或静态脚本检查都不能代替 Godot 运行时通行证明。

## 3. 大区域、子区域与 Godot 场景的关系

采用以下三级模型：

1. **大区域（A0–A13）**：玩家地图与世界叙事中的地理单元，例如 A2 森林、钟墓与旧朝圣路。
2. **子区域（A2-S01 等）**：玩家能够辨认的空间单元，例如雾林地面、钟墓外圈、钟墓坑底、树冠栈道、旧朝圣高路、东部沟壑与林下绕行。
3. **Godot 场景（`.tscn`）**：实际加载、碰撞、镜头、绘制和转场的技术单元。一个子区域可以跨多个场景，一个场景也可以包含多个小型子区域；拆分必须基于运行时需求和空间连续性，而不是为了凑场景数量。

### 适合拆成独立场景的情况

- 通过有意义的洞口、门、升降机、坠落井或长距离通道进入另一块独立空间。
- 独立空间有自己的镜头范围、环境表现、碰撞组织或加载需求。
- 一组房间在玩家认知上构成一个可识别的地点，但不适合与相邻空间放在同一个运行场景中。
- 某个地下区、塔楼或大型竖井具有独立的上下层结构和多个出入口。

### 不应为了拆场景而拆分的情况

- 连续地形中只有普通高低差或一小段跳台。
- 频繁切场景会切断玩家对同一地标、同一空间或一段连续坠落/攀爬路线的认知。
- 场景边界仅由地图网格决定，却没有入口、视线、环境或玩法上的理由。

### 每个场景边界必须登记

- 场景 ID 与所属大区域 / 子区域。
- 入口和出口 ID、所在高度层、方向及实体承托。
- 进入与返回的出生侧、出生坐标、碰撞安全区。
- 是否需要能力、道具、机关状态或灵视门槛。
- 初次不可达、远端解锁、永久开放等状态。
- 与附近地标的视线关系。
- 对应的静态检查，以及尚未完成的主角实机验收。

## 4. A2 作为第一项空间拓扑重审样板

A2 不再按“平台链”继续扩建，而是以已有子区域合同为基础，重新检查各空间之间的真实连接：

- A2-S01 雾林地面：入口方向识别与第一个多向分叉。
- A2-S02 钟墓外圈：地面绕行、钟墓入口和通往高层的空间线索。
- A2-S03 钟墓坑底：可下探并能返回的低位探索空间；H02 不能成为 C03 的主线门槛。
- A2-S04 树冠栈道：与地面保持视觉联系的高位路线，并承担 C03 的空间连接合同。
- A2-S05 旧朝圣高路：远端开启后形成的高位捷径，不得退化成地面门。
- A2-S06 东部沟壑与林下绕行：不同高度的两种路线，落入低处后必须有合理回返路径。
- A2-S07 东部树冠延伸段：让 C03 出现在探索后的远端，而不是从入口处沿直线就能抵达。

A2 的验收重点不是平台数量或地图总宽度，而是玩家能否真正经历“看见路线—选择分支—发现死路或新空间—回头—从另一层重新认识地点—打开捷径”的探索过程。

A2 的 C03（A2→A3）、C04（A2→A5）和 H02 可选入口合同必须保留。若新地形与现有门锚点、出生点或剧情条件冲突，应先修正空间实现并记录影响，不可静默改变这些连接的设计含义。

## 5. 全地图施工顺序

### W0 — 盘点现状

- 以拓扑 JSON 为世界连接基准。
- 对每个 `.tscn` 登记实际所属的大区域 / 子区域。
- 对照 24 条跨区连接和 73 条区域内连接，区分“有合同”“有代码”“有实体地形”“静态检查覆盖”“实机通过”。
- 不以文档中的路线图推断场景已存在或已可玩。

### W1 — 锁定全局拓扑与场景拆分

- 检查 14 个大区域的相对方位、宏区关系、垂直层次和跨区捷径。
- 每个大区域展开为节点图，明确分叉、死路、回环、上下层转换和返回路径。
- 明确每个连接由同一场景内的通道完成，还是通过场景切换完成，并解释原因。
- 对任何需要能力/状态的连接登记可见提示和首次不可达状态。

### W2 — 灰盒实现

- 优先构建连续地面、墙体、竖井、坡道、楼梯、平台和实际通道，再加入必要的场景边界。
- 暂时不放敌人、Boss、NPC、道具和剧情触发；阻断主角通行的关键交互占位除外。
- 所有跨场景门和出生点必须落在实际可站立的地面/平台上，并避开门触发区，防止切场景后立即重复触发。
- 让高低层通过真实通道连接，禁止只在拓扑图上用一条线代表可达性。

### W3 — 主角全图探索验收

- 按自然流程走通主线，但不把主线顺序误当成唯一探索顺序。
- 逐一检查分叉、死路、回头路线、捷径、单向落差、能力门槛、死亡恢复、休整和 Continue。
- 记录每个失败点的场景、入口、出生侧、坐标和复现步骤。
- 只有完成实机走图的连接才可标为运行时通过。

### W4 — 内容填充

灰盒与主角通行验收达到阶段门槛后，再按空间职责放置敌人、Boss、NPC、收集品、机关、环境叙事和剧情事件。内容应服务于空间探索，而不是把地图重新变成线性任务走廊。

## 6. 对照参考作品的研究结论

参考《空洞骑士》时，借鉴的是空间组织方法，而非复制它的地图图形、房间布局、地点命名或具体内容。

- Team Cherry 在访谈中描述了从中心区域向外扩展、先建立区域形状与移动路线，再细化房间连接和内部结构的过程。
- 开发团队强调区域之间的连接与回访体验；随着开发推进，他们也逐步减少了原先过于线性的能力门槛。
- 相关制作研究记载了先用简单瓦片验证房间导航，再添加美术与敌人/互动内容的灰盒流程。
- 因此，本项目采用“世界拓扑 → 区域内部路线 → 场景拆分 → 可走灰盒 → 主角验收 → 内容填充”的顺序，而不是“平台/敌人先摆满，再用门把场景串起来”。
