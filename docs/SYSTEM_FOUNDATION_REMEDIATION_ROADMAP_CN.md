## 1. 当前阶段的实施原则

先审计和建立可复现基线，再修复已确认的系统缺陷；不因看到复杂代码就贸然重写，也不把静态检查冒充 Godot 实机通过。每项工作标记为：

- **CONFIRMED**：源码证据已确认的问题。
- **IMPLEMENTED_UNVERIFIED**：已有实现，但未完成必要的运行验证。
- **MISSING**：当前源码中缺少所需能力。
- **DESIGN_BLOCKED**：需要先确定规则，不能擅自补写。
- **VERIFIED**：有可复现检查及明确结果支持。

## 2. 已确认的优先风险

### P0 — 存档与游戏状态可靠性

1. `scripts/core/world_state.gd` 同时承载大量运行时状态、剧情事实、背包、能力、隐藏探索、房间存档和旧存档迁移。先绘制状态所有权与序列化清单；在没有字段级证据前，不进行大规模拆分。
2. 主存档 `user://nereis_hero_save.json` 与房间状态 `user://room_world_state.json` 分开保存。需验证两者的读写错误、缺字段/类型错误、重复 ID、版本迁移、重置语义，以及新游戏是否会遗留旧房间数据。
3. `prepare_scene_runtime()` 会重置暂停、输入锁、时间缩放与部分能力状态。需检查所有场景切换入口是否一致调用，且失败加载后不会遗留黑屏、输入锁或错误的运行状态。
4. 继续游戏由 `get_resume_scene_path()` 和多个位置/场景 ID 映射决定。需验证映射中的路径存在，出生点/方向和持久位置相符，并处理旧存档中的未知位置。

### P0 — 场景与系统边界

1. 既有架构审计已确认多个场景常驻结构仍由脚本构建，尤其共享区域控制器、A0 序章、部分 Hero 战斗组件及 HUD 菜单。必须按“常驻结构迁移到场景树、瞬时对象可实例化独立场景”的原则分批处理。
2. `scripts/world/world.gd` 与旧区域场景存在不同的房间装配方式。需追踪真实入口与引用，不在证明用途前删除任一体系。
3. `scenes/boot.tscn` 暴露地图验收入口；这可能是开发功能，不应直接删除。先决定发布构建如何隐藏/隔离调试入口，同时保持开发验收能力。
4. 地图、门、拾取物、检查点等常驻节点不能通过运行时脚本代建。运行时可以改变这些已存在节点的状态。

### P1 — 基础玩法与用户体验

- 主角移动/跳跃/攻击/闪避/受击/死亡的状态切换与输入映射。
- 敌人与 Boss 的生命、受击、死亡、阶段切换及门锁条件。
- 交互焦点唯一性、拾取去重、物品查看、背包状态与存档一致性。
- HUD、暂停菜单、叙事面板和场景切换之间的暂停/输入锁互斥。
- 简体中文、繁体中文、英语、日语的关键 UI 文案覆盖与回退行为。
- 调试模式不得污染正式存档，正式启动入口不得依赖开发测试场景。

### P1 — 剧情系统接入准备

当前 `scripts/core/ending_evaluator.gd` 仍使用旧原型阈值（共鸣、遗物数量、隐藏区域数量和旧来源标记）。现有剧情审计已明确：不能在正式剧情事件 ID、道具持有/曾取得/消耗语义未对齐前，直接猜测条件并重写结局求值器。

本阶段先保证事件事实可记录、可保存、可迁移、可测试；剧情条件的最终映射另按剧情合同执行，不在本路线图里擅自裁定。

## 4. 评审原则：不要为了“整理”而制造新风险

- **支持重构的理由：** 状态所有权清晰、场景可编辑、存档与场景切换更可靠，可降低后续剧情和地图扩张的返工。
- **反对一次性大重写的理由：** WorldState、Hero 与共享区域控制器横跨多条现有流程；一次性拆分可能破坏存档兼容、节点路径、跨区合同和旧测试。
- **裁定：** 小批次、先证据后修改、每批同步更新文档；只有引用证据证明无用的实现才可删除。
- **暂停条件：** 发现可能造成软锁、存档丢失、场景入口不可达或正式剧情条件冲突时，先记录证据并停止受影响范围的修改。

## 5. 验证边界

仓库静态检查、自动化脚本、Godot 4.6.1 编辑器检查、Godot 实机流程测试是不同层次。每项结果必须分别记录。没有运行 Godot 的环境时，不得将运行时行为标记为通过。

## 6. 本路线图的首个执行动作

从批次 A 开始，优先审计 `WorldState` 的全部持久字段、主存档与房间存档读写、所有场景切换入口，以及继续游戏的场景/出生点映射。确认这些合同后，再进入代码修改，避免先修外围功能却被存档和生命周期问题反复推翻。


## 7. 首个系统修复：新游戏隔离房间持久状态（2026-10-29）

### 源码证据

- `WorldState` 使用独立文件 `user://room_world_state.json` 保存 `explored_room_ids`、`opened_shortcut_ids` 与 `collected_room_item_ids`。
- 原 `reset()` 清空主存档字段，但未清空上述三个数组，也未重置 `current_a2_room_scene_path`。
- 因此，新游戏删除主存档并调用 `reset()` 后，独立房间存档仍可能保留上一周目的探索、捷径与拾取记录；后续 `load_room_state()` 会再次载入这些旧记录。

### 本次修改

- 在 `reset()` 中清空三个房间状态数组，并将空状态写回独立房间存档。
- 将 `current_a2_room_scene_path` 恢复到默认 R01 房间路径。
- 代码提交：`8cdd6c25058f53074fb4b8e91dc0d8618d83c5c1`。

## 9. 新游戏与存档可靠性第一轮整改（2026-10-29）

### 本轮已实现

1. **主存档原子替换**
   - 先写入临时文件并 flush/close，再将旧档保留为 .bak，最后替换正式存档。
   - 新档提交失败时尝试恢复备份，避免直接以空文件覆盖唯一存档。
   - 新存档增加 save_format_version；拒绝加载比当前支持版本更新的存档，避免旧版程序把新版字段读入后覆盖。
2. **存档有效性检查**
   - 增加 WorldState.has_valid_save() 与 save_load_status，区分缺档、有效、损坏/字段类型错误、读写失败和不支持的未来版本。
   - 继续游戏不再只检查文件是否存在；无效存档会阻止进入游戏，并以对应语言提示玩家。原始存档不会被这条路径自动删除。
   - 兼容没有 save_format_version 的旧档（按版本 0 处理），但要求存在基础字段 current_location 和 hero_memory。
3. **房间持久状态**
   - 房间探索/捷径/拾取状态也改为临时文件 + 备份 + 替换。
   - 读取时检查三个字段是否为数组，并清理空 ID 和重复 ID；损坏文件保留，不静默覆盖。
4. **新游戏初始化**
   - 增加显式 start_new_game()，先退出调试地图存档保护模式，再统一重置周目状态并保存初始存档。
   - 标题菜单改为调用此入口，避免从地图测试返回后因调试标志残留而阻止新游戏初始化。
5. **上一轮无存档流程修复**
   - 无存档时“继续游戏”留在标题菜单，不再错误进入 A0。
