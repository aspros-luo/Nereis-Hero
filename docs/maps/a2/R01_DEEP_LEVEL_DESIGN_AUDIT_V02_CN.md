# A2-R01 深度关卡重构：证据审计与体验设计 v0.2

> 分支：`feature/story-map-progression`  
> 状态：设计基线与风险审计已建立；当前场景仍是待验证实现，不能视为已验收。  
> 原则：先证明玩家体验与地形逻辑，再修改场景；不以 Tile 数量、平台数量或静态可达性替代关卡质量。

## 0. 本轮审计结论

本轮先读取了当前分支上的以下真实文件，而不是仅沿用旧报告：

- `scenes/rooms/a2_fog_forest/a2_r01_forest_crossroads.tscn`
- `resources/tilesets/a2_forest_terrain_tileset.tres`
- `scripts/levels/a2_room_runtime.gd`
- `tools/validate_a2_room_scene_geometry.py`
- `docs/maps/a2/R01_TILEMAP_IMPLEMENTATION_V01_CN.md`

确认的事实：

1. R01 当前场景是 1792×1200 的 Node2D，含三个序列化 TileMapLayer 和独立碰撞多边形；它在 Godot 编辑器中有节点结构，但这本身不证明图块视觉、碰撞轮廓和实际玩法一致。
2. TileSet 将 SVG Atlas 按 32×32 切片，并声明 8×4 的图块来源。当前资源没有定义自动地形连接规则；不能仅凭“有 TileMapLayer”推断它已具有成熟、连贯的地形边缘与过渡。
3. 当前场景把西侧入口、中央钟墓、东侧古树树冠、隐蔽凹口和 R04 下坠入口放在同一空间，但旧规格主要通过平台坐标描述，没有先证明玩家在进入、观察、误判、发现、回环时会获得什么体验。
4. `a2_room_runtime.gd` 仍继承 `greybox_world_region.gd`，并在运行时创建 Hero、UI、出口等。地形主体声称由子场景编辑器可见地创建；后续改动必须继续保持这一点，不能改成代码生成地形。
5. 现有验证脚本明确将 R01 的精确移动可达性延后到 Godot 实机验收。因此，之前的静态 PASS（如有）不能用作跳跃手感、真实碰撞、导入正确或连接实机通过的证据。

## 1. 设计问题：R01 必须让玩家学会什么？

R01 不应只是“森林里有几层平台”。它应建立玩家对 A2 雾林的第一份空间认知：

- **初次理解：** 从西侧进入，玩家能辨认一条可继续前进的路线，也能注意到古树高处的路径，但不必一次看懂整个区域。
- **错误但合理的判断：** 中央下陷地形看起来像一处危险的地裂；观察边缘、根系与旧石材后，玩家逐渐理解它与钟墓坑道相连。
- **垂直发现：** 高位树根不是任意摆放的跳台，而是古树根系、断裂木桥与侵蚀岩层共同形成的可行走结构。
- **主动选择风险：** R04 的下坠口应当由地形、落差和可见深度传达风险；玩家能绕过它继续主路线，也能主动选择坠落。
- **空间记忆改变：** 至少有一条路线或捷径让玩家回头时意识到“原来我之前看到的地方与这里相连”，而不是只获得一件道具。
- **环境叙事：** 石阶断裂方向、被根系抬起的墓石、磨损的行路标记和沉积层应共同暗示这里发生过什么，不依赖旁白解释。

## 2. 原始参考材料与取证方式

### A. 实际游戏空间，而非二手地图印象

取样研究：
- 《空洞骑士》遗忘十字路口：入口识别、主路径与可见但暂时不可达区域。
- 《空洞骑士》苍绿之径：地形轮廓、视线遮挡、自然形态如何成为路径。
- 《黑暗之魂》一处可验证的捷径区域：第一次通过的空间理解，以及开启捷径后的回程变化。

每个案例记录：玩家入口位置、第一眼可见地标、主路线、可选路线、不可达目标、垂直关系、回环、捷径开启前后路线长度、失败后的恢复成本。不要照抄房间坐标或美术外观，只提取空间机制。

参考入口：
- PC Gamer：How to design a great Metroidvania map — https://www.pcgamer.com/how-to-design-a-great-metroidvania-map/
- Godot 4.6 TileMapLayer 官方文档 — https://docs.godotengine.org/en/4.6/classes/class_tilemaplayer.html

### B. 本项目的一手工程证据

优先级高于推测：
1. Hero 控制器源码中的实际速度、重力、跳跃速度、可变跳、空中控制与碰撞体。
2. R01 场景、TileSet、SVG Atlas 的实际资源内容和导入结果。
3. Godot 4.6.1 运行时的玩家轨迹、落点、碰撞调试显示、场景切换日志。
4. R01 与 R02/R03/R04 的双向连接契约及出生点。
5. 已确定的世界生态与叙事约束：A2 是雾林十字路口；R02 为树冠路线；R03 为钟墓；R04 是下坠后可探索的坑底；隐藏区域可选，不得阻断主线。

若源码参数与旧文档不一致，以当前分支源码和实机测量为准，并在记录中注明差异。

## 3. R01 空间结构提案（体验先行，不是最终坐标）

配套的第一版体验地形提案图已加入仓库：[R01_EXPERIENCE_TERRAIN_PLAN_V01.svg](./R01_EXPERIENCE_TERRAIN_PLAN_V01.svg)。该图是可编辑的 SVG 设计草图，不是实机截图或最终施工图；它表达的是路线关系、地形因果和体验节点。施工时必须用实际场景坐标与碰撞节点复核，不能直接将示意图当作可达性证明。

### 区域 I：西侧根台——建立方向感

- 保留明确的入口落脚面，入口附近不要立刻塞入高频跳跃。
- 从安全观察点可看到远处古树轮廓与中央低地的部分线索，但遮挡应保留未知信息。
- 主路线沿不规则根台缓降，不使用等间距、等宽的连续平台。
- 地形解释：粗根从坡体穿出，托住薄土；部分根被切断或腐朽，造成自然高差。

### 区域 II：中央塌陷——形成路线选择

- 中央低地由侵蚀、坍塌和墓道沉陷共同解释，避免单纯矩形地坑。
- 让玩家能从上方观察到部分钟墓结构；真正入口需要走近或从更低角度辨认。
- R04 下坠井不是隐形传送点：井沿、断根、向下延伸的雾和可辨识的落差都应提示“可坠落，但有风险”。
- 主要通路必须能绕过落井；落井是主动选择，不是强制坠落陷阱。

### 区域 III：古树根系——垂直路线与远景目标

- 高位路线应由主干、粗根、断桥残木与岩层共同构成，避免像楼梯一样整齐上升。
- 入口侧能看见高位路径的一部分，玩家暂时无法到达的部分要有明确的空间原因。
- 高位终点连接 R02；R02 返回 R01 的入口必须落在真实可站立的树冠平台上。
- 高位路线与中央路线之间至少有一个可读的垂直关系，让玩家在后来回看时能重新理解中央区域。

### 区域 IV：根石暗隙——隐藏探索

- 隐藏空间入口使用环境线索：不自然的根系空隙、石封裂纹、被磨亮的边缘或微弱的光/雾差异。
- 不要求像素级撞墙。首次发现应来自观察和尝试，不依赖碰巧碰到某个精确坐标。
- 隐藏空间提供环境叙事、道具或空间视角奖励；不承担主线通行的必要条件。

### 区域 V：回看与回环

- 回程应尽可能利用玩家已经认识的地标，而不是让玩家穿过一串重复平台。
- 若 R01 内暂时没有可实现的门闩式捷径，不要伪造一个“捷径已存在”的连接；可以先通过高低路径汇合与视线回看建立空间记忆，再在跨区连接设计确认后补真正的捷径。
- 所有单向落差都要明确标注：可返回、需要绕行返回，或有意作为单向路线。不得出现没有设计意图的软锁。

## 4. 移动约束测量（禁止凭感觉定最终跳距）

实测并记录以下数据：

| 指标 | 取证方法 | 用途 |
|---|---|---|
| 地面速度与空中水平控制 | 读取控制器并在测试场景记录位置/速度 | 计算水平可达范围 |
| 重力、跳跃初速度、可变跳 | 读取控制器并记录释放跳跃后的轨迹 | 估算垂直包络 |
| Hero 碰撞体与脚底参考点 | Godot Visible Collision Shapes | 防止视觉落地但碰撞体穿透/悬空 |
| 平台有效宽度与落点余量 | 实机多次起跳与落地 | 区分理论可达和实际舒适 |
| 下落与恢复 | 记录坠落点、切换触发时机、出生点 | 防止误切场景、软锁和碰撞体内出生 |

理论模型只能用于筛查明显不可能的连接。最终判断以当前 Hero 在 Godot 4.6.1 中的真实运行结果为准。

## 5. 施工顺序

1. **审计基线：** 核对 Hero 控制器、R01 地形、TileSet/Atlas、房间连接和资源导入条件。
2. **体验图：** 先画玩家路径图，标出入口、视线、主路、可选路、下坠口、隐藏空间、回看点和回程。
3. **剖面图：** 用 2–3 张地形剖面表达西侧根台、中央塌陷、古树高路之间的真实高度关系。
4. **移动包络：** 测出 Hero 的跳跃与落地限制，给每个关键跳跃标注设计余量。
5. **编辑器施工：** 修改 `.tscn` 中可见的 TileMapLayer、TileSet、碰撞多边形与 Marker2D；不要通过脚本运行时生成地形。
6. **资源核验：** 确认 Atlas 每种图块的轮廓、边缘和透明度在 Godot 中正确导入；如果图块视觉无法区分地表/土层/装饰，先修资源再铺图。
7. **工程测试：** 跑静态合同检查、Godot 场景解析、可见碰撞调试与真实路线切换。
8. **盲测：** 由未参与设计的人试玩，不告知隐藏空间位置，记录误解、失败、发现与回程时间。
9. **迭代：** 先修复阻断理解/通行的问题，再调节细节。不得把“增加平台数量”作为默认修复方案。

## 6. 独立验收：哪些证据能证明它有效？

### 工程正确性
- Godot 4.6.1 无解析错误、缺失资源和导入错误。
- 地形节点在编辑器中可见、可直接编辑；碰撞形状与可见地形边缘一致。
- 必经路线可用当前能力通行；关键跳跃有实机落地证据。
- R01↔R02、R01↔R03、R01→R04 及其约定返回路线在正确高度生成。
- 下坠口只有在实际进入井口区域时才切换场景，普通跳过不会误触发。
- 所有单向落差、出生点、返回点和门槛有明确的合同。

### 体验正确性
- 未受提示的测试者能辨认主要方向，但不必立刻理解全部支路。
- 可见但暂不可达的目标能激发探索，而非让人误以为游戏坏了。
- 至少一个发现改变测试者对空间连接的理解。
- 隐藏入口能通过环境线索被发现，不要求像素级撞墙。
- 失败后能恢复，重复回程不会变成无意义的长距离跑图。

### 可复核性
- 保存参考分析、坐标与剖面图、关键跳跃视频、碰撞调试截图、测试问题清单和修复记录。
- 报告区分“静态检查通过”“Godot 场景解析通过”“运行时通过”“盲测通过”。
- 没有证据的项目标记为“待验证”，不得写成 PASS。

## 8. 当前场景几何审计观察

从现有 R01 `.tscn` 读取到的关键碰撞轮廓：

- `Ground_West` 从入口地面延伸至 x=640，最后一段平台高度 y=736。
- `Platform_001` 从 x=704 开始，最高边缘为 y=704，主体延伸至场景底部。
- `Platform_002` 从 x=1216 开始，顶部为 y=640，主体同样延伸至场景底部。
- `DropToR04` 标记位于 (672, 780)，正好处在前两块大型地形之间的缺口附近。
- `Platform_003` 至 `Platform_014` 是若干 32px 高的局部平台，其中一组集中在 x=224–704，另一组集中在 x=832–1792。

这些是场景文件中的坐标事实，不代表角色一定能按预期通过。特别需要在实机中检查：

1. 64px 的主要缺口是否读作有意的落差，而非碰撞断层；
2. R04 下坠触发是否与实际井口的可见轮廓对齐；
3. 大型地形主体是否在视觉上造成不自然的整片实心墙，或与 TileMapLayer 的表面/土层图案错位；
4. 树冠返回点 (1504, 480) 与钟墓返回点 (960, 704) 是否能安全落在正确的碰撞面上；
5. 现有平台组是否形成可读的自然路线，而非“等高小台阶排队”。

在完成这些验证前，不应批量增加平台，也不应把碰撞轮廓整体重写成另一套未经实机验证的地形。

## 9. 本轮完成定义

本轮设计工作完成后，R01 不仅要“更复杂”，而应具备：可解释的地形因果、可读的主路线、能重塑空间认知的探索、实测可行的移动、可恢复的失败，以及可由独立测试者复核的证据。R02/R03/R04 的接口保持不变，除非接口冲突被明确记录并经验证后修改。
