## 门与交互机制基线

- 普通出口由 `_spawn_exit_door()` 创建，Area2D 的 RectangleShape2D 为 110×80，形状偏移 (0,-35)。在地面 y=540 的门，触发区约为 y=465..545。C13 和 C22 高位门都位于门根节点 y=400（floor_y - 140），触发区约为 y=325..405；仍需按各自支撑平台验证落地与交互。
- 普通门的交互还需要进入 Area2D 并赢得共享 interaction focus；普通门优先级 100。
- 灵视秘密门使用 80px 的径向距离判定，焦点优先级 25。门不是实体阻挡墙；高位路线仍需在 Godot 中实测是否可从地面绕行。
- 区域有连续地面碰撞体，平台使用 one-way collision。

## 死亡恢复与休整点

- `_spawn_hero()` 在每个区域入口将检查点设为主角实际出生坐标。
- 死亡时 Hero 脚本先发出 defeated 并立即把主角传送到 checkpoint；区域脚本随后等待 0.75 秒，再重设速度、再次传送到 checkpoint，并调用 restore_full()。本轮已在等待期间锁定 `WorldState.input_locked`，在恢复开始/结束清理共享交互焦点，降低主角在两阶段之间移动、门焦点残留或重复交互的风险。仍需运行时检查动画、无敌时间与物理同步。
- 休整点位于 (rest_x,floor_y)，交互半径 110px；使用后恢复状态、把检查点保存为主角当前位置并写入存档。
- 七个目标区域休整点：A6 x=1300、A7 x=1320、A8 x=1150、A9 x=1100、A10 x=1200、A11 x=1050、A12 x=1360。源码坐标上，它们没有与 C11/C13/C14/C15/C19/C21/C22 门同点；A8 休整点距 x=930 的王墓侧门约 220px，距 C15 x=2310 很远。
- C13 的入口检查点在高位平台上，平台坐标与出生点吻合；后续若调整平台，必须同步检查点支持。普通地面休整点由连续地面承托。
- 目前不能仅凭源码确认实际角色碰撞形状、焦点竞争、死亡瞬间的物理帧或存档恢复时机。

## 本轮新增：验收矩阵与静态几何复核（2026-10-15）

### C13 两端与地面跳跃边界

- A7 → A8：门中心 x=map_width−72，门根节点 y=floor_y−140；目标 A8 出生 x=190、y=floor_y−120，平台 Rect2(80,420,150,18) 承托。
- A8 → A7：门中心 x=72，门根节点 y=floor_y−140；目标 A7 出生 x=2340、y=floor_y−120，平台 Rect2(2200,420,370,18) 承托。
- 当前主角 JUMP_VELOCITY=-520、GRAVITY=1400，理论跳高约 96.6px；按 48px 高角色碰撞体估算，地面起跳最高时角色顶部约 y=419，C13 触发区底部约 y=405，存在约 14px 垂直间隔。站在 y=420 平台时角色顶部约 y=396，触发区有约 9px 重叠。
- 静态推导的目标是让平台可交互而地面跳跃不可触发；这不是 Godot 物理帧实测。需分别从两端进出，验证落地、门焦点和跳跃中 Area2D 是否意外触发。
- 连续地面碰撞体仍横贯地图，门本身不是实体墙。因此验收重点不是“能否走过门的 x 坐标”，而是从地面跑到门下、跳跃触碰触发器、是否能不走上层平台就转场。若仍可触发，应将 C13 设计成需要上层平台专属交互区/实体阻挡，而不能仅依赖视觉高度。

### 死亡恢复重复测试

在 A7、A8 分别执行至少 5 次连续死亡；另在 A6/A9/A10/A11/A12 的休整点各执行一次：
1. 记录死亡发生前位置、当前 checkpoint、WorldState.input_locked。
2. 在 0.75 秒恢复等待期内反复按左右、跳跃、攻击、E；预期输入锁期间不能移动、攻击或触发门/休整点。
3. 恢复后确认 velocity == Vector2.ZERO、生命/体力已恢复、输入锁解除、焦点组无旧门残留。
4. 检查主角胶囊底部是否由平台/地面承托；确认恢复点不在 C13/C15/C19/C21/C22 门触发区中。
5. 连续死亡后再转场、存档重载一次，排查 respawning 卡住、输入锁未解除、双重恢复导致重复触发。

源码已检查恢复控制器在等待前锁输入、前后清理交互焦点；Hero 自身仍会先立即传送到 checkpoint，区域控制器 0.75 秒后再恢复一次。动画与物理帧行为必须在 Godot 实测。
